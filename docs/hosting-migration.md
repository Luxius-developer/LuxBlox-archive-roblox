# Перенос LuxBlox: Render, Neon и игровой сервер

## Что работает на Render

Сейчас `server.app` — Python HTTP API и страницы WebView: регистрация, вход, аккаунт/пароли, баланс, Premium, друзья, сообщения, настройки, каталог/инвентарь, миниатюры и лайки. Все постоянные данные находятся в Neon PostgreSQL. Перезапуск Python не должен удалять их. SQLite — только для локальной разработки.

Текущий origin: `https://luxblox-api.onrender.com`. Владелец проекта: пользователь Luxius с неизменяемым ID **2**. Права привязаны к ID, не к username. Изменять этот ID при переносе нельзя без явного решения владельца.

Render принимает публичный HTTP/WebSocket-трафик на одном порту: https://render.com/docs/web-services#port-binding. Этого достаточно для перечисленных API. Текущий Dockerfile не содержит игровой движок. Сохранённый `places/LuxBlox-Starter-Obby.rbxlx` — карта, а не запущенная игровая сессия.

## Быстрый перенос API с сохранением данных

1. Сохранить приватный резервный `pg_dump` Neon и текущие переменные окружения в защищённое место. Не добавлять DATABASE_URL, пароли, ключи или дамп в git.
2. На новом Linux/Docker-хосте собрать имеющийся `Dockerfile`. Без Docker: Python 3.10+, `pip install -r requirements.txt`, затем `python -m server.app --host 0.0.0.0 --port "$PORT"`.
3. Передать ту же `DATABASE_URL` из защищённой настройки хостинга. Сохранить `LUXBLOX_REQUIRE_PERSISTENT_DATABASE=1`, `LUXBLOX_OWNER_USER_ID=2`. Базу Neon переносить вместе с API не требуется.
4. Настроить HTTPS-прокси. Указать `LUXBLOX_PUBLIC_ORIGIN=https://новый-домен` без пути. Домен используется для ссылок на аватары, миниатюры и одежду. Куки требуют HTTPS; не включать insecure-local-cookies на внешнем адресе.
5. Проверить `/healthz`, вход существующего пользователя, сохранённый баланс и аватар, заявки/дружбу, инвентарь и голоса. POST/PATCH должны сохранять CSRF-защиту. Проверить закрытый доступ к `/admin` для обычного аккаунта.
6. Пока APK содержит старый Render-origin, сохранить Render как обратный HTTP-прокси на новый origin или подготовить новый APK. Публичный стабильный собственный домен в будущих APK упростит последующие переносы.
7. Перед окончательным переключением остановить старый API, если он больше не служит прокси; действующие учётные записи остаются в Neon. После рестарта обновить страницы форм: CSRF-токены выданы процессом и могут стать недействительны. Сеансы входа сохраняются в БД.

## Пересборка APK под новый origin

Использовать **тот же приватный ключ подписи**, тот же package `com.luxius.luxblox` и больший versionCode. Исходный подписанный R6 хранится в приватном GitHub Releases, тег `android-r6`.

Перенос требует пересмотра всех трёх слоёв адресов:

- Java: `tools/patch_client.py:endpoint_map/patch_methods` и класс `com.roblox.client.u`. Полный `patch()` предназначен для свежего исходного APK `com.roblox.clienc`, он намеренно откажет на уже пропатченном пакете.
- WebView: `tools/LegacyLinks.smali` содержит authority Render и должен использовать новый домен. Сохранить точную проверку исходных доменов, HTTPS и посторонние ссылки.
- OBB: шесть модулей из `tools/patch_lua_routes.py`, включая Url.lua. Все сервисы должны оставаться путями `/friends`, `/avatar`, `/catalog` и т. п. на одном origin. Не превращать их в поддомены нового хостинга.

После сборки: проверить package, versionCode, подпись/выравнивание, точные изменённые файлы и сохранение нативных библиотек/CA. Проверка подписи не заменяет проверку запуска на телефоне. Старые APK могут содержать дополнительные нативные адреса, которые ещё не охвачены Java/OBB-патчерами.

## Что нужно для настоящей игровой сессии

Нужен совместимый с клиентом 2021 игровой runtime RCC, его разрешённый способ запуска, стартовая конфигурация карты и доступный из интернета игровой порт. Python управляет API и сессиями, но не реализует физику/репликацию Roblox. Наличие Python/Rust в панели не означает наличие RCC. Если runtime рассчитан на Windows, Linux-панели дополнительно потребуется поддерживаемая среда запуска; это нужно подтвердить по конкретному runtime.

У сервера 256 МБ RAM / 25% CPU неизвестны ОС, разрешённые процессы и сеть. Без запуска конкретного RCC нельзя честно подтвердить, что хватит даже на одну карту. На три параллельные карты рассчитывать нельзя. Сначала выяснить свободную RAM с учётом уже работающей задачи, разрешение на runtime/контейнер/Wine, выделенный порт и возможность ограничить пробу одним игроком. Существующие файлы и задачи не удалять и не останавливать ради пробы.

После появления runtime: отдельный процесс карты, затем защищённый обмен с HTTP API, выдача клиенту реального адреса/порта и параметров соединения. Только после успешного входа на телефоне включать `isPlayable=true`. До этого карточка доступна в `/games`, голоса сохраняются, а кнопка показывает сообщение об отсутствии сервера. Настоящее окно Kick возможно только при работе игрового клиента/сервера; страница WebView не доказывает подключение.

## Что проверять после каждого обновления

CI проверяет SQLite и PostgreSQL; реальные интеграционные проверки должны идти в изолированной базе/ветке. Проверить запрет бесплатных Robux и админских действий обычным пользователям, Premium/галочки после рестарта, получение/принятие заявок, надевание только принадлежащих предметов, приватность сообщений/инвентаря и уникальность голоса пользователя на плейс. Реальные платежи отключены: `/checkout/unavailable` отдаёт визуальную 404 без обработки денег.

## Уточнение R7

Для нового APK требуется также `tools/patch_native_bundle.py`: прежний перечень Java и шести Lua-модулей не охватывал DataModelPatch.rbxm. Подробности и уточнение найденной версии RCC: [android-r7.md](android-r7.md). Windows RCC 0.450 найден в форке Blue7366/OpenPekora, но его совместимость с клиентом 0.477 и работа в 256 МБ не проверены.
